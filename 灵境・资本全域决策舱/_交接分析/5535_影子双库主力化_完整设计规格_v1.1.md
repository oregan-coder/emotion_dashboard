# 1. 影子库命名与建模约定

## 1.1 `_dim`

用途：稳定代理键和维度映射。

### `batch_dim`

权威职责：

```text
batch_int  <->  batch_id
```

约束：

```sql
PRIMARY KEY(batch_int)
UNIQUE(batch_id)
```

所有新 `_fact` 表优先使用 `batch_int` 作为内部 join key；对外回执仍保留 `batch_id` 文本键。

规则：

- `batch_int` 仅内部代理键，不进入业务语义；
- API / report / revision 仍以 `batch_id` 作为稳定外部标识；
- 禁止跨环境假设同一 batch_id 对应相同 batch_int；
- 跨库/导出时永远携带 batch_id。

---

## 1.2 `_fact`

用途：规范化事实行。

特征：

- 一行代表一个业务事实粒度；
- 大 payload 不直接存正文，只保留 `blob_id`；
- 通过 `batch_int`、code、factor_id、trade_date 等形成查询索引；
- 不应与旧名表长期双权威。

---

## 1.3 `_ref`

用途：稳定指向某一 head/revision/blob 或兼容旧结构的引用层。

例：

```text
p50_ref
```

规则：

- `_ref` 只保存轻量索引/指针；
- 不复制大正文；
- ref 必须可解析；
- 无法解析时属于完整性错误，不自动 fallback 到其他 revision。

---

## 1.4 `master_*`

用途：跨 batch 的去重主数据或版本索引。

### `master_member(batch_int, frame, code, blob_id)`

建议唯一键：

```text
(batch_int, frame, code, blob_id)
```

### `master_versions`

用于记录 master 数据版本：

```text
sha256
created_at
row_count
batch_count
```

其角色是迁移/版本证明，不作为二进三业务评分真值表。

# 2. 权威表归属

影子库切换后必须采用“每类业务只有一个权威写入面”。

## 2.1 最终权威原则

### 批次/研究/证据事实

权威：

```text
batch_dim
batches_fact
research_rows_fact
source_rows_fact
quote_fact
metrics_fact
history_fact
history_assets_fact
dashboard_derived_metrics_fact
s02b_revisions_fact
s02lp_inputs_fact
source_receipts_fact
```

### 旧名表

例如：

```text
source_receipts
s02b_revisions
quote_observations
s02lp_inputs
```

切换后定位：

```text
兼容读层 / 迁移期历史表 / legacy bridge
```

**不得继续作为新业务事实的第二权威写入面。**

---

## 2.2 双写策略

不建议长期双写。

切换前允许：

```text
旧库正式写
+
影子库镜像迁移/验证
```

切换日开始：

```text
影子双库 = 唯一正式写入
旧库 = 冻结只读冷备
```

不设置长期“双写过渡期”。

理由：

- 双写失败会重新制造版本分叉；
- 已有 first_batch 问题说明指针/事实一致性必须收敛到单一事务链。

# 3. 证据库正式读写契约

## 3.1 blob 写入

统一函数：

```text
put_blob(raw_bytes, encoding)
```

步骤：

```text
raw_bytes
→ sha256(raw_bytes)
→ 查询 ev_blob.sha256
→ 已存在：复用 blob_id
→ 不存在：zlib.compress(raw_bytes)
→ INSERT ev_blob
→ 返回 blob_id
```

约束：

```text
sha256 UNIQUE
blob_id PRIMARY KEY
orig_len = len(raw_bytes)
zlib_len = len(zlib_data)
```

`encoding`：

```text
utf-8-json
utf-8-text
binary
```

禁止把 Python 对象 repr 当证据正文。

---

## 3.2 blob 读取

统一：

```text
get_blob(blob_id)
→ 查 ev_blob
→ 校验 zlib_data
→ zlib.decompress
→ len(raw)==orig_len
→ sha256(raw)==stored sha256
→ 按 encoding 解码
```

失败必须返回明确错误：

```text
BLOB_NOT_FOUND
BLOB_ZLIB_ERROR
BLOB_LENGTH_MISMATCH
BLOB_SHA_MISMATCH
BLOB_ENCODING_ERROR
```

不得静默返回空字符串。

---

## 3.3 `zunzip` / shim 正式归属

建议正式化为：

```text
emotion5535_shim
```

只负责**读取兼容桥**：

- 注册 `zunzip(blob_id)`；
- 根据 `.evidence_path` 找证据库；
- 只读打开 evidence；
- 不承担生产写入。

生产写入不得经 `zunzip`，而应调用显式 EvidenceStore。

# 4. 跨库连接契约

## 4.1 路径来源优先级

统一配置文件：

```text
data/store_paths.json
```

示例：

```json
{
  "hot_db": "data/.migration_shadow/market_store_5535.next.sqlite3",
  "evidence_db": "data/.migration_shadow/evidence_5535.next.sqlite3",
  "schema": "5535_OPERATIONAL_STORE_V1"
}
```

`.evidence_path` 仅作为兼容桥输入，不再作为唯一事实源。

---

## 4.2 生产写连接

```text
HOT: read-write
EVIDENCE: read-write
```

由同一 orchestration 持有。

业务提交顺序：

```text
1. evidence put_blob
2. hot facts 写入 blob_id
3. hot 指针提交
```

由于 SQLite 跨文件事务不是真正单文件原子事务，必须使用**发布状态机 + 可验证幂等补偿**，不能声称两个文件绝对原子。

---

## 4.3 只读复盘

```text
HOT: mode=ro
EVIDENCE: mode=ro
```

要求：

- query_only=ON；
- generation guard；
- 文件 identity 在同轮稳定；
- evidence_path 与配置绑定一致。

# 5. `_fact` 表约束与索引基线

以下是设计约束，不冒充当前影子库已存在。

## 5.1 `batches_fact`

建议：

```sql
UNIQUE(batch_int)
INDEX(trade_date)
INDEX(stored_at)
INDEX(mode, trade_date)
```

并通过 batch_dim 解析外部 batch_id。

---

## 5.2 `research_rows_fact`

粒度：

```text
(batch_int, code, factor_id)
```

建议唯一：

```sql
UNIQUE(batch_int, code, factor_id)
```

索引：

```text
INDEX(batch_int, code)
INDEX(code, factor_id)
INDEX(factor_id, batch_int)
```

---

## 5.3 `source_rows_fact`

粒度：

```text
(batch_int, source_name, source_key, blob_id)
```

索引：

```text
INDEX(batch_int)
INDEX(source_name, batch_int)
INDEX(blob_id)
```

---

## 5.4 `quote_fact`

建议粒度：

```text
(observation_date, code, frame, source, batch_int)
```

索引：

```text
INDEX(observation_date, code)
INDEX(batch_int, code)
INDEX(frame, observation_date)
INDEX(blob_id)
```

---

## 5.5 `metrics_fact`

建议：

```text
UNIQUE(batch_int, metric_id, code_nullable)
INDEX(metric_id, batch_int)
```

---

## 5.6 blob_id

所有事实表中的 blob_id：

- 热库不声明 SQLite 跨库 FOREIGN KEY；
- 由应用级 integrity checker 维护；
- 切换验收要求 100% 可解析。

# 6. 迁移完整性对账

行数不能直接旧表 = fact 行数。

采用 5 层对账。

## L1 日期/批次覆盖

```text
旧库 trade_date 集合
vs
影子 published_days / batch_dim / batches_fact
```

要求正式发布日期集合一致，明确允许排除的测试批次单列。

---

## L2 业务对象数量

按：

```text
trade_date
batch_id
code
factor_id
frame
```

比较**业务唯一键数量**，不是表物理行数。

---

## L3 payload 哈希

随机 + 关键日期全量：

```text
旧payload canonical sha
vs
影子 ev_blob 解压后的 canonical sha
```

重点日期：

```text
9/16
9/17
9/18
切换日前最近3个交易日
```

---

## L4 指针完整性

每个 published_days：

```text
first_batch_id → batch_dim → batches_fact
batch_id       → batch_dim → batches_fact
```

必须 100% 可解析才允许正式切换。

---

## L5 业务回归

至少核对：

- 9/18 96/96评分；
- 9/16历史修订107/108；
- 9/17→9/18五只结果；
- 9/16→9/17九只结果；
- 市场宽度、砸盘、最高板、五日周期固定日期值；
- 主站核心 API 业务指纹。

---

# 7. 指针完整性修复原则

当前发现部分日期 first/current 在 batch_dim 暂不可解析。

切换前处理原则：

1. 先只读分类：
   - `MIGRATION_NOT_IMPORTED`
   - `SOURCE_MISSING`
   - `POINTER_WRONG`
   - `BATCH_DIM_MISSING_MAPPING`
2. 不允许人工造 batch；
3. 若旧库仍存在原始 batch：
   - 按迁移器规则重新迁入；
   - 保留原 batch_id；
   - 建立 batch_dim；
4. 若旧库原 batch 本身也不存在：
   - 保留 `ARCHIVE_GAP`；
   - 不用 revision 顶替 first；
   - 不能阻塞未来新日期发布，但在历史回测中标记不可用。

# 8. 正式切换 checklist

切换必须全部满足：

## 数据
- meta.schema 正确
- batch_dim 无重复 batch_id
- 当前生产日期 current pointer 100% 可解析
- 切换日起所有 first pointer 可解析
- blob_id 引用完整
- 关键业务回归通过

## 写入
- 正常日更在影子库完成一次完整 PUBLISHED
- 自动评分成功
- revision 新增成功
- T+1 outcome 写入成功或只读生成契约明确

## 读取
- 5000 主站读影子库
- 5108 读影子库
- 自管启动器读影子库
- T+1/评分任务路径一致
- `s02b_meta.attached_version` 与新读桥契约一致

## 备份
- 旧库完整 SHA256
- 旧库压缩冷备
- 影子热库切换前备份
- evidence库切换前备份
- 配置备份
- 回退脚本验证

满足后：

```text
CUTOVER_READY=true
```

# 9. 切换动作

1. 暂停新日更任务进入；
2. 等所有 jobs 终态；
3. 旧库最后一次只读快照与 SHA；
4. 影子双库完整性检查；
5. 修改统一 `store_paths.json`；
6. 启动服务；
7. 运行 smoke：
   - 主站5000核心API
   - 二进三评分
   - 5108读取
   - evidence解压
8. 执行一次 no-op/只读回归；
9. 恢复日更；
10. 下一次真实日更必须在影子库得到 PUBLISHED；
11. 标记：

```text
CUTOVER_ACTIVE
```

旧库从此冻结只读。

---

# 10. 回退方案

回退窗口：建议至少 **10个交易日**。

触发：
- 新库无法完成正式 PUBLISHED；
- 关键业务结果与旧库基准不一致；
- blob 解压大面积失败；
- 主站核心接口不可用；
- 指针/版本关系异常。

回退动作：

1. 停止影子写任务；
2. 保存影子故障快照；
3. 恢复旧库配置；
4. 主站/任务重新指向旧库；
5. 不把影子失败日的半成品回灌旧库；
6. 形成 incident report。

---

# 11. 旧库删除前置条件

以下全部满足才允许物理删除旧 1.4GB 单库：

1. 影子库稳定运行 >=10个交易日；
2. >=5次完整日更 PUBLISHED 成功；
3. 至少2次T+1自动沉淀成功；
4. 主站5000/5108/评分/日更均已无旧库路径；
5. 关键历史日期对账通过；
6. 新增数据不存在旧库独占写入；
7. 旧库冷备已生成：
   - `.sqlite3` 原文件或无损压缩
   - SHA256
   - 文件大小
   - 最后更新时间
   - schema dump
8. 回退演练至少成功一次。

删除的是**在线工作副本**，冷备至少保留一个完整开发/模型验证周期；建议 90 天。

# 17. 尚未完全拍板的业务规则补充

以下沿用 v1.0，但修正几个空洞。

## 17.1 情绪覆盖空洞

若 E 分落在任何未命中状态：
- 默认用 E区间基础状态；
- 再应用风险覆盖规则；
- 不允许 `state=null`。

弱修复连续确认：
- 第1天满足 → `RECOVERY_CANDIDATE`
- 第2个连续交易日仍满足 → `WEAK_RECOVERY`
- 中间任一日不满足则重置。

## 17.2 S1/S4 UNKNOWN

主线 coverage 只统计已知权重：

```text
coverage = known_step_max_points / 100
```

总分不按比例放大。

状态判定使用已知分，但 MAIN_CONFIRMED 必须：
- coverage>=0.60
- S2已知
- S5已知

S1/S4未知不自动记0。

## 17.3 情绪仓位 vs 五日资金周期仓位

两者不是同一个指标。

- 五日资金周期七档是受保护的**资金周期建议**；
- 情绪状态产生的是**情绪风险上限**。

最终展示仓位：

```text
display_position_cap =
min(five_day_position, emotion_position_cap)
```

不把二者加权平均。

注意：这是研究风险上限展示，不自动形成交易权限。

## 17.4 INVALIDATED 在无盘中源时

若竞价/盘中数据源不可用：
- 预案只能形成静态 `WAIT / OBSERVE`；
- `INVALIDATED` 不自动触发；
- 页面显示 `INTRADAY_GATE_DISABLED`。
