# 1. 2.1 定稿：fact 表继续以文本 `batch_id` 为正式 join key

## 1.1 最终决定

**不在首次 cutover 前把所有 `_fact` 表改造成 `batch_int` join。**

现状已经确认：

- `batches_fact.id` 为 32 位文本 batch_id；
- `research_rows_fact.batch_id`
- `source_rows_fact.batch_id`
- 其他 fact 表

都已经围绕文本 batch_id 形成事实关系。

因此 v1.2 正式修订：

```text
batch_id TEXT = 事实层正式业务关联键
batch_int      = batch_dim 内部代理键 / 排序键 / 可选优化键
```

### 允许 batch_int 的用途

- 内部压缩型索引；
- 导出排序；
- 后续性能优化；
- 新建表的辅助外键。

### 禁止

- 不允许开发方假设所有 fact 已含 batch_int；
- 不允许 cutover 前重写几十万事实行，只为了“结构更漂亮”；
- 不允许把 batch_int 暴露成跨环境稳定 ID。

## 1.2 新业务表的键

新业务表统一保存：

```text
batch_id TEXT
```

可选附加：

```text
batch_int INTEGER NULL
```

但 `batch_id` 必须存在。

这样与当前影子库事实模型保持兼容。

# 2. 2.2 索引计划：切换前必须补齐

## 2.1 原则

索引创建放在：

```text
迁移完整性对账之后
正式 cutover 之前
```

要求：

1. 所有写任务停止；
2. WAL checkpoint 完成；
3. 热库冷备完成；
4. 单写窗口执行；
5. 创建后 `ANALYZE`；

# 3. 2.3 batch_dim / published_days 指针收敛

## 3.1 已知现状

- `batches_fact = 77`
- `batch_dim = 75`
- `published_days = 19`
- 9/10、9/11：first/current 均有不可解析项
- 9/14、9/16、9/18：first 不可解析，current 可解析

## 3.2 处理顺序

对每个 dangling pointer：

### A. pointer 对应 batch 在 `batches_fact` 存在

但 batch_dim 缺映射：

```text
classification = BATCH_DIM_MISSING_MAPPING
```

允许迁移器补：

```text
batch_dim(batch_id)
```

不改 batch_id，不造业务 batch。

### B. pointer 对应 batch 不在 batches_fact，但旧库有原始 batch

```text
classification = MIGRATION_NOT_IMPORTED
```

迁移器重新导入该原始 batch，再建立 batch_dim。

### C. 旧库也不存在

```text
classification = SOURCE_MISSING
historical_status = ARCHIVE_GAP
```

**不得用 current revision 顶替 first。**

### D. pointer 本身错误

只有当来源证据能证明 published_days 指错 batch 时：

```text
classification = POINTER_WRONG
```

才允许修复。

## 3.3 9/10 / 9/11 日期集合判定

L1 正式发布日期集合优先级：

```text
published_days
> confirmed publish receipt
> batches_fact 中 mode=PUBLISHED 的明确记录
> 普通 BACKFILL / TEST batch
```

不能因为 `batches_fact` 有 9/10 batch 就自动把 9/10 当正式发布日。

### 输出

```text
publish_date_classification.json
```

每个日期标：

```text
FORMAL_PUBLISHED
BACKFILL_ONLY
TEST_ONLY
ARCHIVE_GAP
UNRESOLVED
```

# 4. 2.4 Canonical Hash v1

## 4.1 JSON

输入是 JSON 时：

1. UTF-8 解码；
2. parse JSON；
3. 递归保留数值原类型；
4. `json.dumps`：
   - `sort_keys=True`
   - `ensure_ascii=False`
   - `separators=(',', ':')`
   - 禁止 NaN/Infinity
5. UTF-8 编码；
6. SHA-256。

定义：

```python
canonical_json = json.dumps(
    obj,
    sort_keys=True,
    ensure_ascii=False,
    separators=(",", ":"),
    allow_nan=False,
)
sha256(canonical_json.encode("utf-8"))
```

## 4.2 JSON 数值注意

不把：

```text
1
1.0
```

强制视为相同值。

如果旧源和新源类型不同，报告：

```text
CANONICAL_TYPE_DIFFERENCE
```

而不是偷偷归一。

## 4.3 文本

非 JSON 文本：

- UTF-8；
- 统一 CRLF/LF 为 `\n`；
- 不 trim 首尾空白；
- SHA-256。

## 4.4 二进制

直接 raw bytes SHA。

## 4.5 无法解析

若声明 encoding=`utf-8-json` 却解析失败：

```text
CANONICAL_PARSE_ERROR
```

不得 fallback 成普通文本后宣布一致。

# 5. 2.5 `model_factor_view` 定稿：应用层 View，不建 SQLite VIEW

## 5.1 原因

`research_rows_fact` 的 factor_score 在 blob JSON 中；
SQLite VIEW 若调用 `zunzip()`，每个新连接都必须先注册 UDF，过于脆弱。

因此正式设计：

```text
model_factor_view
```

是**应用层只读投影**，不是数据库 CREATE VIEW。

## 5.2 过滤条件

只接受：

```text
research_rows_fact.factor_id IS NOT NULL
AND kind = 'factor'
AND batch 对应 FORMAL_PUBLISHED / selected revision
AND batch mode NOT IN ('BACKFILL','TEST')
```

如果真实 kind 值与 `factor` 不一致，以 schema/sample 审计后写入配置：

```text
factor_row_kinds.json
```

## 5.3 字段路径

当前尚未有足够附件证明 blob 的最终字段路径，因此开发前 P0-1 工具必须抽样：

- 每个 factor_id 至少1条；
- 输出 JSON path inventory；
- 自动识别候选字段；
- 人工/GPT核对后冻结为：

```text
factor_blob_contract_v1.json
```

至少需确定：

```text
factor_score
factor_max
known
qualification
formal_score
rank
rules_version
```

**在字段路径未冻结前，不允许正式模型评价。**

# 6. 2.6 Blob 完整性检查器

## 6.1 Fact → blob

扫描所有含 blob_id 的 fact 表：

```text
dangling_blob_refs
```

每条包含：

```text
table
row_key
blob_id
batch_id
code
```

切换条件：

```text
dangling critical refs = 0
```

## 6.2 Blob 本体

逐 blob 检查：

```text
zlib decompress
orig_len
sha256
encoding decode
```

输出：

```text
BLOB_ZLIB_ERROR
BLOB_LENGTH_MISMATCH
BLOB_SHA_MISMATCH
BLOB_ENCODING_ERROR
```

## 6.3 orphan blob

可报告但首次 cutover 不阻断：

```text
ORPHAN_BLOB
```

因为去重证据可能历史上暂未被现存 fact 引用。

## 6.4 输出

```text
blob_integrity_report.json
```

# 7. 正式文件路径定稿

不长期把正式主库放在 `.migration_shadow`。

## 7.1 cutover 后正式路径

```text
data\market_store_5535.sqlite3
data\evidence_5535.sqlite3
```

## 7.2 shadow 在 cutover 前

```text
data\.migration_shadow\market_store_5535.next.sqlite3
data\.migration_shadow\evidence_5535.next.sqlite3
```

切换时不“直接覆盖”现有同名库。

采用：

```text
1. 停止写入
2. 备份旧正式库
3. shadow checkpoint
4. rename/move shadow 到正式路径
5. 更新 store_paths.json
6. 启动服务
```

Windows 同卷 `os.replace()` 优先。

## 7.3 旧库

移动到：

```text
backup\pre_shadow_cutover\
```

而不是留在 `data` 目录继续被误识别。

# 8. 双文件一致备份

由于 HOT/EVIDENCE 是两个 SQLite 文件：

## 8.1 备份前

1. 停止所有写 job；
2. 确认 jobs 全终态；
3. HOT `PRAGMA wal_checkpoint(TRUNCATE)`；
4. EVIDENCE `PRAGMA wal_checkpoint(TRUNCATE)`；
5. 记录：
   - file size
   - mtime
   - SHA256
   - `PRAGMA data_version`
   - `schema_version`

## 8.2 备份

使用 SQLite backup API 或关闭写连接后文件复制。

生成：

```text
backup_manifest.json
```

必须同时记录两文件 SHA。

## 8.3 备份后

只读打开两个备份文件，执行：

- meta.schema
- blob checker
- published pointer checker
- 关键业务 smoke

通过才标：

```text
CONSISTENT_DUAL_BACKUP=true
```

# 13. Evidence retention / 容量策略

首次 cutover 不删除 ev_blob。

P1 才做 retention。

原则：

1. 正式发布、revision、评分、T+1、模型评价用到的 blob 永久保留；
2. raw transient debug blob 可按 90/180 天策略；
3. orphan blob 先报告，不立即删；
4. 删除必须满足：
   - 无任何 fact/ref 引用
   - 非正式发布链
   - 非模型验证样本
   - 已过保留期
5. evidence 库超过：
   - 5GB：开始容量审计
   - 10GB：必须实施 archive plan

归档单位建议按月/季度，而不是随机逐 blob 删除。

# 16. 当前结论

v1.2 的核心策略是：

**不把“理想新 schema”强行压到当前影子库。**

首次 cutover 前：
- 文本 batch_id 继续作为事实主键；
- batch_int 保留为辅助代理键；
- 先补索引、指针映射、blob完整性、路径统一、备份与回退；
- 先让影子库安全成为唯一正式主力；
- 更深层的存储结构优化放到 cutover 后的版本迁移。

这是风险最低、最符合当前影子库真实物理状态的方案。
